# 用户管理与权限控制设计文档

**日期**：2026-04-07
**状态**：已确认（v1，待实现规划）

---

## 需求概述

本次需求聚焦企业场景下的用户管理与权限控制，目标是在现有 LobeHub 代码基础上补齐以下能力：

- 用户注册 / 登录支持邮箱验证
- 平台支持 API Key 认证能力
- 平台存在三级全局角色体系：普通用户、开发者、企业管理员
- 支持账号分组管理，用于权限控制与协作
- 同组成员可看到本组全部话题
- 同一时刻每个话题只允许一个人访问，其余成员可见但不可进入
- 管理角色可查看其管辖范围内的组话题

本次设计遵循以下约束：

- 平台全局角色与组内角色分离
- 保留现有 `group_admin / member` 组内角色，不用三级平台角色替代
- 话题锁只限制访问，不限制可见性
- 第一版不开放 “管理员查看下辖用户全部个人私有话题”

## 二、设计目标与范围

### 2.1 设计目标

本次实现目标为：

1. 固化三级平台角色体系
2. 保留现有组内角色体系
3. 建立 “用户管理哪些用户组” 的管理范围模型
4. 明确并固化 “可见性” 和 “访问性” 两层规则
5. 在不推翻现有 `/ug` 方案的前提下补齐权限闭环

### 2.2 本次范围

**纳入范围**

- 平台全局角色定义与权限映射
- 管理范围模型
- 用户组话题的可见性与访问控制改造
- 相关后端路由权限改造
- 必要的管理页面增强
- 测试补充与验收标准

**不纳入范围**

- 管理员查看下辖用户全部个人私有话题
- API Key 作为 SPA 主登录态
- 独立企业后台重构
- 多租户体系重构
- 重写 `/ug` 页面视觉与交互结构

## 三、角色模型设计

### 3.1 平台全局角色

继续复用现有 RBAC 表结构，不新增新的角色系统。

新增或固化以下系统角色：

- `basic_user`：普通用户
- `developer`：开发者
- `enterprise_admin`：企业管理员

这些角色落在现有：

- `rbac_roles`
- `rbac_user_roles`
- `rbac_role_permissions`

### 3.2 角色职责

#### `basic_user`

- 使用平台基本功能
- 可访问自己创建的个人话题
- 可查看自己所属用户组下的全部组话题
- 不可进入企业管理页

#### `developer`

- 在 `basic_user` 基础上，拥有 “范围内管理” 能力
- 可查看自己被授权管理范围内的用户组与组话题
- 可进入受限的企业管理入口
- 不拥有全局用户管理权

#### `enterprise_admin`

- 拥有全局企业管理能力
- 可进入 RBAC 管理、用户组管理、管理范围管理页面
- 默认拥有全范围组话题可见能力

### 3.3 组内角色

保留现有 `user_group_members.role`：

- `group_admin`
- `member`

组内角色只处理组内管理行为：

- 添加成员
- 移除成员
- 修改组信息
- 绑定 Agent

组内角色不承担平台级角色语义。

## 四、管理范围模型设计

### 4.1 设计原则

“管辖下用户” 在第一版中统一转译为 “管辖下用户组”。

即：

- 管理者不直接管理单个用户
- 管理者管理一个或多个用户组
- 用户属于某个被管理组，即视为该管理者范围内用户

这种设计的优点：

- 与现有 `user_groups` 数据结构天然一致
- 与 “同组成员共享组话题” 的业务模型一致
- 能复用 `parentId` 支持层级继承

### 4.2 新增表建议

新增一张管理范围映射表：

`user_group_managers`

建议字段：

- `user_id`
- `group_id`
- `created_at`

第一版无需引入复杂 `scope` 字段，继承关系可在查询层根据 `user_groups.parent_id` 推导。

### 4.3 范围继承规则

- 若用户被授予管理某个父组，则默认拥有其所有子组的管理范围
- 企业管理员默认拥有全范围，无需写入 `user_group_managers`
- 普通用户没有管理范围

### 4.4 范围判定接口

服务端应抽象统一的范围判定能力，例如：

- `getManageableGroupIds(userId)`
- `canManageGroup(userId, groupId)`
- `canViewGroup(userId, groupId)`

后续所有与用户组话题相关的查询与动作统一调用这些判定方法，避免在不同 router 中重复散落权限逻辑。

## 五、话题可见性与访问控制

### 5.1 核心原则

本次设计明确区分：

1. **可见性**
   用户能否看到某个组及其话题列表
2. **访问性**
   用户能否真正进入某个具体话题

### 5.2 可见性规则

#### 普通用户

- 可查看自己创建的个人话题
- 可查看自己所属用户组下的全部组话题

#### 开发者

- 拥有普通用户的全部可见范围
- 额外可查看自己被授权管理范围内的全部组话题

#### 企业管理员

- 可查看全部用户组及其全部组话题

### 5.3 访问性规则

访问具体组话题时继续使用现有 `topic_locks` 机制。

规则如下：

- 未锁定：有权限用户均可进入
- 已被自己锁定：自己可继续进入
- 已被他人锁定：自己可见但不可进入

因此，锁的职责是：

- 限制 “进入 / 占用”
- 不限制 “列表可见”

### 5.4 第一版边界

第一版不开放：

- 管理员查看下辖用户的全部个人私有话题

第一版开放：

- 管理员查看其管理范围内的组话题

这样可以避免在缺少显式 “个人私有 / 共享 / 可监管” 分类字段的情况下扩大隐私边界。

## 六、后端改造设计

### 6.1 认证链路

**保持现状**

- Better Auth 继续负责主站登录态
- OpenAPI 继续支持 API Key Bearer Token 认证

**本次不做**

- 不将 API Key 接入 tRPC 主上下文

### 6.2 RBAC 角色与权限映射

需要补充系统角色初始化与权限映射策略。

建议：

- `basic_user`：基础登录使用权限
- `developer`：企业功能只读 / 范围管理能力
- `enterprise_admin`：`user:manage`、RBAC 管理、用户组管理、管理范围管理

后端校验仍以权限码为准，而不是在业务代码里大量硬编码角色名。

### 6.3 用户组路由改造

当前 `src/server/routers/lambda/userGroup.ts` 中：

- 管理类操作依赖 `user:manage`
- 使用类操作依赖 “是否为组成员”

本次需把使用类操作从：

- **仅组成员可用**

升级为：

- **组成员或拥有该组可见 / 管理范围的用户可用**

受影响的接口包括：

- `getGroupTopics`
- `createGroupTopic`
- `tryLockTopic`
- `renewLock`
- `releaseLock`

### 6.4 `topicId` 级动作的二次权限校验

这是本次必须补齐的安全边界。

当前诸如：

- `tryLockTopic(topicId)`
- `renewLock(topicId)`
- `releaseLock(topicId)`

若只依赖前端已知 `topicId`，存在越权可能。

因此所有 `topicId` 级动作执行前，都必须：

1. 反查该 `topicId` 所属 `userGroupId`
2. 校验当前用户是否对该组具备可见权限
3. 校验锁状态是否允许该动作

### 6.5 范围判定服务

建议新增独立服务或模型方法，集中实现：

- 当前用户是否是企业管理员
- 当前用户可管理哪些组
- 当前用户可查看哪些组
- 组层级递归展开

避免在以下位置重复拼装权限逻辑：

- TRPC router
- Topic model
- UserGroup model

## 七、前端改造设计

### 7.1 企业设置入口

现有设置页企业入口主要在：

- `src/routes/(main)/settings/hooks/useCategory.tsx`

当前逻辑主要依赖 `user:manage`。

本次原则：

- 前端菜单显示可继续基于权限控制
- 但服务端校验必须是最终安全边界

### 7.2 用户组管理页

现有页面：

- `src/routes/(main)/settings/user-groups/features/GroupList.tsx`

本次建议扩展能力：

- 允许为开发者 / 管理员配置管理范围
- 保持现有组成员管理与 Agent 绑定逻辑

若管理范围 UI 在第一版实现成本过高，可先提供基础入口并以后续迭代增强。

### 7.3 `/ug/:ugid` 页面

现有 `/ug` 页面继续保留。

行为调整为：

- 组成员可进入并查看本组全部话题
- 管理范围内开发者可进入并查看其范围内组的话题
- 企业管理员可进入任意组查看话题
- 具体进入某个话题时仍受锁约束

### 7.4 锁状态展示

继续沿用现有设计：

- 话题列表显示锁状态
- 已被他人占用的话题不可进入
- 已被自己占用的话题可继续进入

不因锁而隐藏话题条目。

需要新增或补充以下测试场景：

## 九、验收标准

本次功能完成后，需满足以下验收条件：

1. 新用户可通过邮箱注册 / 登录，邮箱验证能力正常可用
2. 平台存在并可分配三类系统角色：普通用户、开发者、企业管理员
3. 企业管理员可进入并使用 RBAC 与用户组管理能力
4. 开发者仅可查看其被授权管理范围内的用户组与组话题
5. 同组成员可以看到本组全部话题
6. 同一时刻每个话题仅允许一个人访问
7. 被占用话题对其他成员保持可见，但不可进入
8. 所有 `topicId` 级访问动作都经过服务端权限校验
9. 现有 `/ug` 页面主链路不发生功能回归

## 十、实施建议顺序

建议按以下顺序推进实现：

1. 固化系统角色与权限映射

7. 补齐测试与回归验证

## 十一、最终结论

本次需求不需要推翻现有用户组聊天实现。

推荐方案是在现有 Better Auth、RBAC、`user_groups` 与 `topic_locks` 基础上增量补齐：

- 平台三级角色
- 管理范围模型
- 组话题的范围可见性
- 话题级独占访问安全边界

其中 “同组成员可见全部话题，但每个话题同一时刻只允许一个人访问” 应作为本次设计的核心业务规则，并在查询、锁控制、前端展示与测试中统一贯彻。
